# 生图教程计划

## 场景和缺口

用户提交图片要求，上游调用发生超时。网站必须保留“结果待确认”，不能把同一任务重新排队并让用户再次付费。

真实基线见 [教程索引](../README.md)。[`generation_jobs`](https://github.com/JeanphiloGong/image-studio/blob/main/db/001-initial.sql) 只有状态枚举；[`tests/schema.test.mjs`](https://github.com/JeanphiloGong/image-studio/blob/main/tests/schema.test.mjs) 的 `unknown generation outcomes can be retained without retrying` 只是插入并读取 `uncertain`，并未调用重试或状态转换逻辑。首页没有提交处理器，当前不存在任务模型、持久化服务或 worker。

## 当前版本 V0 的目标与非目标

这是你亲自建模的第一个推荐版本：先让一条关键业务规则成为真实代码中的可执行行为。它不承诺用户已经能生成图片，也不证明并发、持久化或上游的计费行为。

状态名称沿用当前 schema：`queued`、`running`、`succeeded`、`failed`、`uncertain`。以下方法与字段是建议的新实现，尚未存在，不把 SQL 状态枚举误认为已有对象。

### 建议的最小模型

使用一个具体的 `Job` 及明确命名的方法即可，不引入状态机框架、通用仓储接口、事件总线或额外架构层。字段只包含本版真正验证的任务 ID、本站用户与网关归属、提示词／画幅／模型快照、状态，以及完成结果或错误摘要。不包含余额、`credit_cost`、预占或退款方法。

创建时校验必要身份有效、提示词与现有长度范围一致（按字符计数）、画幅在现有选项内；不硬编码尚未验证的真实模型。状态和固定参数不对调用者开放任意赋值入口，只提供实际需要的读取方式与行为方法。状态转换不得改变任务归属或参数。未知或非法转换返回错误且不留下部分修改。

| 当前状态／事件                                       | 结果               | 本版规则                            |
| ---------------------------------------------------- | ------------------ | ----------------------------------- |
| 有效请求创建任务                                     | `queued`           | 固定归属和输入，不扣费              |
| `queued` + 开始执行                                  | `running`          | 当前对象只能开始一次                |
| `running` + 已取得可交付的结果引用                   | `succeeded`        | 保存结果引用；完整资产持久化留到 V2 |
| `running` + 结果明确的失败                           | `failed`           | 不代表一定未收费，也不改变余额      |
| `running` + 超时／连接中断                           | `uncertain`        | 没有证据就不判断远端是否执行        |
| `running` 再次开始，或任意终态／`uncertain` 再次开始 | 返回错误，状态不变 | 无隐式重试                          |
| `succeeded`、`failed` 或 `uncertain` 再写其他结果    | 返回错误，状态不变 | V0 不含核查后的纠正接口             |

V0 中 `uncertain` 暂不能解决；后续 V2 的核查流程须明确凭据后再增加受控转换。任务失败后的新生成是新的显式用户操作，不能伪装成原任务恢复。输入校验失败发生在创建任务前，不额外设计排队取消或失败分支。

## 冻结与验收

采用 Go 方案、正文完整交付以上文件后，在 Image Studio 根目录运行：

```bash
go -C server test ./internal/generation -v
go -C server test ./...
pnpm test
pnpm check
```

预期：任务创建、正常结束、非法转换、超时后禁止重发全部通过；现有六项 schema 测试和前端检查保持通过。失败案例须检查整个对象没有被部分修改，不能仅断言“返回了错误”。

`commit_when`：你能解释上述每条转换，完整检查从指定基线可复现，无网络、支付或本地点数写入；不存在新增后未使用的 helper、包装层或依赖。仅当这些条件真实满足，才可把 V0 模型标为已验证；这不是执行 Git 提交的授权。

本次只核对旧测试与原型检查。Go 模型测试尚不存在、未运行。单对象测试不证明数据库原子性、用户会话隔离、远端严格一次执行或生产迁移安全。

## V1/V2 必须补的边界

V1 需要同用户同幂等键的唯一约束、请求参数一致性检查，以及跨用户相同键互不冲突。并发 worker 通过数据库原子认领，只让一个执行者继续；本地模型本身不承担锁的职责。

发送前持久化调用意图。崩溃后无法确定是否发出的调用按待核查处理；不能把所有 `running` 自动重排队。本地测试上游须记录实际接收次数，并注入“已接收但响应丢失”来验证不重发。

V2 核实模型、用户密钥和实际用量关联能力。远端成功但图片保存失败，要能恢复获取结果或保留核查状态，不得再次请求生成。若网关没有可靠查询能力，明确保留人工核查边界，不编造自动恢复保证。

进入 V1 前重新检查源码和基线，细化该版新增迁移、服务、HTTP 调用者、配置及测试文件；目前 V1/V2 是能力路线，不是已可直接实施的逐文件教程。
