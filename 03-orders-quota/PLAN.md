# 订单与额度履约教程计划

## 场景与基线

用户购买额度包，支付平台重复通知；网关充值已经成功，但响应丢失。网站必须区分“已付款”和“额度已确认到账”，恢复时不能给用户再充一次。

本站基线见 [教程索引](../README.md)。[`orders`](https://github.com/JeanphiloGong/image-studio/blob/main/db/001-initial.sql) 只有简化支付状态与旧 `credits`；没有支付交易、通知事件或网关履约记录。旧 `one_purchase_entry_per_order` 只限制本地账本插入，无法证明外部充值只发生一次。

已核对的参考实现：

- 私有参考项目的 `payments.Service.ConfirmPayment`：匹配交易、金额和币种、记录通知、确认付款并调用履约。
- 私有参考项目的 `HTTPClient.CreateAndRedeemCode`：发送额度码、用户和固定 `Idempotency-Key`；该参考方法只返回错误，不提供完整核查结果。
- 私有参考项目的支付通知合同与网关管理合同：用于核对服务端验签和调用边界。

参考项目当前流程含发卡和积分兑换；本站购买后直接履约到 Sub2API，不复制其中间步骤。现有客户端测试验证请求格式，不证明当前生产网关的并发幂等或长期恢复能力；实施前必须核实。

## 你先固定的模型

先区分购买承诺、收款事实与交付结果。订单快照固定服务端商品、金额、币种、应发网关额度、归属和权益范围；交易保存收款关联；履约保存固定身份、同步状态和网关凭据。

付款金额用对应币种最小单位整数。网关额度单位及精度须核对合同后确定，不能直接当成本地点数整数，也不能用未经约定的浮点运算换算用户权益。客户端不能决定价格、额度或计费用户。

V0 可以用同一具体订单模型中的付款匹配和履约身份规则完成验证，无需为每个名词创建仓储接口或单独服务。它接收的是已经验签的付款事实，不能用参数 `verified: true` 冒充实际签名校验。

采用 Go 建议时，V0 的新增目标为 `server/internal/orders/order.go` 与 `order_test.go`；需要时仅补实际使用的履约类型。本站没有这些文件。未来 V1 的交易存储、迁移、HTTP 入口和配置需在选定版本时重新查源码、逐一列出；现在不声称这些调用者已存在。

V0 正文顺序：先创建不可由付款回调改写的购买快照，再约束成功付款的匹配及重复操作，最后生成固定履约身份并区分“已付、待同步、待核查、已确认交付”。每一步同时提供直接可运行检查，并检查拒绝时原状态不变。

V0 不能用内存标志证明跨进程、并发通知或远端操作只执行一次。

## V1 必须完整包含的集成

服务端根据商品配置创建订单和支付交易；回调入口先实际验签，再校验商户、订单、交易引用、金额、币种和成功状态。支付平台浏览器跳转不触发履约。

本地通过事务、唯一约束和条件更新记录收款与待履约事实；对同一订单权益保持同一网关幂等标识和请求参数。数据库事务不能覆盖远端网关操作，不能因为 `ON CONFLICT` 成功就宣称整个跨系统流程只执行一次。

写入网关前持久化履约意图，外部响应丢失后保持待核查，用同一标识查询或按已核实合同重试。不得重新生成额度码或订单身份。不能仅依赖一个有过期时间的 HTTP 幂等缓存承诺长期不重复入账；需验证额度码唯一性、归属和结果核查合同。

本地测试网关须能模拟“已经到账但响应丢失”，同时记录实际发放次数；只有最后余额正确但多次发放后又抵消的实现不算通过。真实网关联调单独进行。

## 验收与冻结

V0 采用 Go 后，正文提供上述完整测试文件，读者在项目根运行 `go -C server test ./internal/orders -v`。覆盖金额、币种、订单和交易引用不匹配；重复合法付款；固定履约身份与购买快照不可被通知改写。当前命令尚不可运行，因为模型未实现。

V1 正文必须给出集成测试命令、测试数据库准备和无需真实付款的签名／通知样例，验证重复事件、同订单不同事件、并发通知、非法签名、错误金额、响应丢失恢复和跨用户查询。真实支付和网关写入作为单独联调，不加入默认测试。

`commit_when`：选定版本所有承诺、调用者和检查完成；V1 还需确认同步中断可以恢复，不遗漏已付订单，不重复发放权益。单元模型通过不等于支付闭环通过。

清理旧本地点数表和测试须与实际持久化切换一起实施。不能把空 SQLite 开发库重建当成生产迁移；若有真实订单、凭据或历史余额，必须另行盘点并核对迁移方案。本次未检查或改动任何部署数据库。
