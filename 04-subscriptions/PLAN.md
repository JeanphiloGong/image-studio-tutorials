# 订阅与权益教程计划

## 场景与基线

用户一次付款购买一个会员周期。会员资格在约定期间有效；商品若含额度，由订单履约直接发到 Sub2API。重复支付通知不能重新延长周期或再次发放权益。

本站还没有订阅模型、表、接口或页面，目标见 [Image Studio 产品规格](https://github.com/JeanphiloGong/image-studio/blob/main/docs/PRODUCT-SPEC.md)。

已核对私有参考项目的 `subscriptions.Subscription`、`CreateInput`、`PostgresStore.Create`、`ActiveByUser` 和 `CancelByUser`：按订单唯一约束复用订阅记录，以结束时间筛选活跃记录，取消会更新状态。这里的幂等 upsert 不核验每种冲突业务含义，不能原样复制后就宣称本站所有重复履约规则已满足。

参考项目的 `Fulfillment` 按起点加 `DurationDays` 计算结束时间；这不等于自然月订阅，也不等于自动续费。参考查询未展示所有未来生效场景所需的规则，本站必须按确定的期间模型检验。

## 正文前需要你确定的语义

1. 周期按固定天数还是自然月，起点按支付时间还是开通时间？
2. 有效期内续购是顺延、独立周期还是暂不支持？
3. 取消是立即撤销当前会员资格，还是到期不再继续？首版没有自动续费，不能用“停止扣款”掩盖实际没有扣款任务。
4. 每次购买包含什么权益？额度一次发放还是分期发放？首版推荐一次性履约，尚不把它当成已确认商品规则。

上述选择影响模型和验收，不能在正文中默默指定。取消不自动退款或清空已发网关余额是已经确定的边界。

## 你先写、Agent 后接的边界

你先写一个具体的 `Subscription` 期间模型，定义时间关系、有效性和取消行为。采用 Go 建议时，V0 新增目标为 `server/internal/subscriptions/subscription.go`、`subscription_test.go`；这些文件当前不存在。

V0 正文必须先根据你选择的规则写出时间例子，再实现对应行为，最后交付完整固定时钟检查。例如选用常见的左闭右开期间后，应验证 `start` 有效、`end` 无效；这只是待确认的建议，不能在选择前作为已冻结契约。使用 UTC 保存绝对时间，面向用户展示的时区单独处理。

agent 在 V1 中补数据库、唯一订单／权益约束、HTTP 与页面，并复用订单模块的额度履约，不再创建另一套充值路径。会员期间成功但额度同步未确认时，两种事实分别记录，重试不能再次创建周期或给用户再次延长有效期。

若同一唯一订单再次提交了不同用户、商品或期间，应识别冲突，不能通过无条件 upsert 把旧记录覆盖成“成功”。这种并发与一致性检查需要在实际数据库集成中验证，不靠单个模型测试证明。

V1 的迁移、调用者、配置和完整检查入口在选定该版本时对照当时真实代码细化。V2 目前仅列未来能力，不能据此宣称自动续费方案已经设计或实现。

## 验收与冻结

V0 采用 Go 后，正文交付完整测试，读者在 Image Studio 根目录运行 `go -C server test ./internal/subscriptions -v`。预期固定时间边界、无效期间、取消和续购全部符合已选择规则。当前尚无这些文件，未运行该命令。

V1 正文提供测试数据库及完整集成脚本：重复订单、不同事件、并发开通、部分履约失败恢复、跨用户拒绝，以及取消不触发网关余额变更。真实支付／额度发放另行联调。

`commit_when`：当前版本的期间规则和验证有明确证据；V1 还须连通本人购买、查询、取消和权益履约，避免只有模型就称订阅已完成。生产可用性另由上线演练检验。
